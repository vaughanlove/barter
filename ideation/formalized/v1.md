# Barter Negotiation - Spec

## (a) Summary
User asks buyer agent MUSE for a product; MUSE searches the VENDOR SITE, obtains a NOTARY attestation of the lowest observed offer as verifiable proof, then iteratively barters with the VENDOR AGENT using that proof as leverage and re-verifies lowness with the NOTARY until convergence, then presents the best offer to the User for approval and executes purchase and delivery.

## (b) Messages
| n | from | to | meaning |
|---|---|---|---|
| 1 | User | MUSE | Request product |
| 2 | MUSE | VENDOR SITE | Search catalog |
| 3 | VENDOR SITE | NOTARY | Request lowest-offer proof generation |
| 4 | NOTARY | MUSE | Return lowest-offer attestation |
| 5 | MUSE | VENDOR AGENT | Barter with proof as leverage |
| 6 | VENDOR AGENT | MUSE | Counter with new offer |
| 7 | MUSE | NOTARY | Verify if new offer is lowest |
| 8 | NOTARY | MUSE | Return updated attestation |
| 9 | MUSE | VENDOR SITE | Repeat search / next round |
| 10 | MUSE | User | Present best offer |
| 11 | User | MUSE | Approve purchase |
| 12 | MUSE | VENDOR SITE | Execute purchase |
| 13 | VENDOR SITE | User | Deliver / confirm receipt |

## (c) Loop semantics
`loop Barter rounds` covers 5-9. Each iteration = leverage attestation to negotiate (5), receive counter-offer (6), re-attest/verify lowness (7-8), re-query storefront (9). Repeats until MUSE decides no further improvement; exit to 10. Original `-- repeat --` arrow is modeled as the loop block, not a single message.

## (d) Code mapping
- NOTARY (`notary/src/server.ts`, dev Ed25519): 3 maps to `POST /attest {domain, transcriptHash}` for lowest-offer transcript; 4 and 8 map to signed attestation returned (consumed by MUSE); 7 maps to `POST /verify {attestation, signature}` or re-attest and `GET /pubkey` for verification. Real core would be MPC-TLS / TLSNotary.
- VENDOR SITE (`vendor/` Vite app): 2, 9 map to search UI/API; 12 maps to checkout/purchase; 13 maps to fulfillment confirmation.
- VENDOR AGENT: 5-6 is off-site negotiation leveraging the attestation.
